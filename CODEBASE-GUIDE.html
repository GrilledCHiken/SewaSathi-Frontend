0 · The 60-second pitch

SewaSathi is a marketplace for home services in Nepal — cleaning, plumbing, repairs, moving, furniture assembly. Someone who needs a job done posts it; a nearby verified worker takes it; the money and the messaging are handled in between.

Three kinds of people use it

  • Customer — posts tasks, hires workers, pays, reviews.
  • Worker — uploads ID documents, waits for approval, then browses and accepts jobs, and gets paid.
  • Admin — approves or rejects workers, suspends accounts, reads inquiries, pulls reports.

How the money moves

  1. Customer posts a task with a budget, say NPR 2,500.
  2. A worker accepts it.
  3. Customer pays a 10% advance (NPR 250) to confirm the booking. Only now does chat unlock and the worker get the go-ahead.
  4. Worker does the job and marks it finished.
  5. Customer pays the 90% balance (NPR 2,250) — by eSewa, Khalti, or cash.
  6. Job closes. Customer can now leave a review.
If you only remember one sentence

"COMPLETED means done and paid for." A worker finishing the work moves a task to AWAITING_PAYMENT, not COMPLETED. Only a settled balance payment closes it, and only a closed task can be reviewed. Every count, every report, and every rating on the site reads that way.

Likely question · "Why is CSRF turned off? Isn't that a vulnerability?"

It is off on the API chain only, and that is the correct setting there. CSRF attacks work because a browser attaches cookies to a request automatically, even one triggered from an attacker's page. Our API doesn't authenticate from a cookie — it needs an Authorization header that JavaScript has to set deliberately, and the attacker's page cannot read our token to set it. So a forged cross-site request arrives with no credentials at all. On the admin console, which does authenticate from an ambient cookie, CSRF is switched on. The reasoning is written into the code at SecurityConfig.java:168-172.

Why DTOs instead of returning entities

Every response is a DTO in dto/response/ with a static from(...) factory — there are no mapper classes. Three reasons, all defensible:

  • Nothing leaks. User has passwordHash, failedLoginAttempts, lockedUntil. UserResponse has none of them.
  • No lazy-loading blowups. spring.jpa.open-in-view=false, so the Hibernate session is closed by the time Jackson serialises. Touching a lazy @ManyToOne at that point would throw. Building the DTO inside the transaction avoids it.
  • The API shape can change independently of the tables.

Schema migrations — there is no Flyway

In development Hibernate patches the schema itself (ddl-auto=update). Production sets ddl-auto=validate, which refuses to start if the entities and the live tables have drifted apart. The gap between them is filled by nine hand-written scripts in backend/src/main/resources/db/.

Two of those scripts are genuinely required, even in development

ddl-auto=update only ever adds — it will create a new column but it will never issue an ALTER TABLE ... MODIFY COLUMN. So:

  • add-requested-task-status.sql — widens the tasks.status ENUM to include REQUESTED. Without it, direct hire fails at the database.
  • add-google-signin.sql — makes users.password_hash nullable, which is what a Google-only account needs.

If asked "why no Flyway?": honest answer — this is a coursework project with a single developer and a schema Hibernate can manage in development; the scripts exist for the changes Hibernate cannot make. Flyway would be the right call the moment a second person or a second environment is involved.

4.1 · Customer signup with email OTP

What the user sees

They fill in name, email, phone and password on /signup/user and press Create account. The page moves to /signup/verify and asks for a six-digit code. The code arrives by email. They type it — the form submits itself the moment the sixth digit lands — and they are sent to the login page with a green "Account created" banner.

The one design decision to lead with

Pressing "Create account" does not create an account. It parks the details in a separate pending_registrations table and emails a code. The row in users only comes into existence when that code is sent back. So an email address that was mistyped, or belongs to someone else, never reaches the accounts table at all — and every account on the site is provably attached to a mailbox its owner can open.

The subtle bit — noRollbackFor

completeRegistration is annotated @Transactional(noRollbackFor = OtpException.class). Without it the whole feature breaks silently: RegistrationOtpService.verify joins this transaction rather than opening its own, so when a wrong code throws, the transaction would roll back — including the attempt-counter increment it just made. The counter would reset to zero on every wrong guess and the five-attempt cap would never be reached. This is an excellent thing to be asked about, because the answer shows you understand transaction propagation rather than having copied an annotation. AuthService.java:109-115

Small security detail worth mentioning

An unknown challenge token throws exactly the same error as a wrong code. There is no way to use this endpoint to discover whether a signup is in flight for a given address. RegistrationOtpService.java:173-178

Resending: POST /api/auth/register/resend enforces app.otp.resend-cooldown-seconds (60) and resets the attempt counter — a new code is a new puzzle. Abandoned rows are swept nightly by a @Scheduled job at 03:15.

4.2 · Worker signup and document verification

What the user sees

Same form and same email code as a customer, plus skills, hourly rate and location. After the code is accepted they land straight on a document-upload step — police clearance and citizenship document, both required — and then a "we'll review this" confirmation. They can sign in immediately, but until an admin approves them, every dashboard route puts the verification screen in front of them and they cannot accept any job.

Step 1 — signup, and an unusual bit of plumbing

Identical to the customer path, but with role=WORKER. The account is created PENDING AuthService.java:128 along with a worker_profiles row built from the skills/rate/location carried through the challenge.

Step 2 uploads documents, which means it needs an authenticated session — so the app has to sign the new worker in automatically the instant the account exists. That means holding their password across two pages. It is not put in router state, because react-router serialises router state into window.history.state, which is persisted by the browser. Instead it lives in a plain module-level variable that is read exactly once and cleared. utils/signupHandoff.js, used at VerifySignupOtp.jsx:73-85. If the auto-login fails, the flow falls back to /login — WorkerLayout will put the verification form in front of them anyway.

4.3 · Login, and the whole token story

What the user sees

Email and password on /login. On success they land on their own dashboard — /dashboard, /worker or /admin depending on their role. They stay signed in across page refreshes and browser restarts, and after long enough idle they are quietly signed out.

The sign-in check, in the order it happens

AuthService.java:232-272. The order is deliberate and is worth explaining unprompted:

  1. Look the user up by email. An unknown address throws exactly the same InvalidCredentialsException as a wrong password — the endpoint cannot be used to discover who has an account.
  2. Is the account locked? lockedUntil in the future → AccountLockedException → HTTP 423 LOCKED, with the number of minutes left.
  3. Is passwordHash null? Then this is a Google-only account, and it says so plainly. That does confirm the address is registered — but signing up already does that with its 409, so nothing new leaks, and leaving them guessing would be pointless when there is no password to guess.
  4. passwordEncoder.matches(raw, hash). On failure, registerFailedAttempt increments the counter; at 5 it sets a 15-minute lock. :40-41, 256-259, 280-288
  5. Only now is suspension checked. Putting it after the password check means an attacker cannot probe whether an account is suspended without already knowing the password.
  6. Reset the counters and mint the tokens.

What is actually inside the JWT

Have this answer ready · "Why isn't the role in the token?"

Three claims only: sub (the email), iat, exp. No role, no user id, no name. That is a choice, not an oversight.

A JWT cannot be recalled once issued. If the role lived inside it, then suspending an account or demoting a user would have no effect until their token expired — they would keep their old powers for up to 15 minutes. Instead JwtAuthFilter re-reads the user from the database on every request JwtAuthFilter.java:42 and refuses outright if they are now suspended :43-44. The cost is one database query per authenticated request — name that cost yourself before the examiner does, and say the trade was made knowingly: revocation that takes effect immediately is worth more here than saving a primary-key lookup.

"Why SHA-256 for the refresh token but BCrypt for passwords?"

BCrypt is deliberately slow, to make guessing a human-chosen password expensive. A refresh token is 256 random bits — there is nothing to guess, so slowness buys nothing, and it would be paid on every single refresh lookup. The reasoning is written into the code at RefreshTokenService.java:165-176.

Rotation and theft detection

Every refresh spends the old token and issues a new one. Tokens in the same session share a familyId.

  1. Token not found → InvalidTokenException.
  2. Token found but already revoked → this is a replay. The genuine client already spent it, so whoever presented it again has a copy. The entire family is revoked and a warning is logged — the session dies rather than the attacker being quietly served. RefreshTokenService.java:77-84
  3. Past absolute expiry, or idle beyond the timeout → revoke the family and throw.
  4. Otherwise: mark spent, issue a replacement that inherits the original expiry :99-102 — so rotating forever cannot extend a session past seven days.
The client-side consequence — and why the interceptor is written the way it is

Because a replayed token is treated as theft, a page that fires four requests on mount and gets four simultaneous 401s must not start four refreshes — the second one would present an already-spent token and destroy the session. So httpClient keeps a single in-flight refreshPromise that every waiting request shares. httpClient.js:30-55

Two more details in that file worth knowing: the refresh call uses a bare axios.post, not httpClient, so that a 401 on the refresh itself cannot re-enter the interceptor and loop; and requests to /auth/ are excluded from retry entirely, because a failed login is a real 401 the user has to answer, not an expired token to renew behind their back.

Where the session lives in the browser

Both tokens go into localStorage under sewasathi_token and sewasathi_refresh_token tokenStorage.js:1-2. The user object is never persisted. On boot, if a token exists, AuthContext calls GET /api/users/me to rehydrate the session and clears the token if that fails AuthContext.jsx:41-51 — so a stale or revoked token can never leave the UI showing a signed-in state.

Signing out clears local storage first and unconditionally, then tries the server call. If the network is down the user is still signed out on this device rather than stuck in a half-session AuthContext.jsx:133-147. The server always answers 204, even for a token that was already invalid — reporting an error would leak whether the token was real. POST /api/auth/logout-all revokes every session on every device.

4.4 · Google Sign-In

What the user sees

A "Sign in with Google" button on both the login and signup pages. A first-time user is asked for one extra thing Google cannot supply — their phone number — and is then signed in. A returning user goes straight through. Someone who originally signed up with a password can also use the button, and it links to the same account rather than refusing.

One endpoint, three answers

POST /api/auth/google returns three different status codes, and the client branches on them. This is unusual enough that it is a very likely question.

  • 200 OK — the account already existed. Signed in.
  • 201 Created — this call created the account. Signed in.
  • 202 Accepted — Google checked out, but we still need a phone number. Nothing has been created. The client collects the phone and posts the same credential back.

It is expressed as a sealed interface GoogleSignInOutcome and a Java 21 pattern-matching switch — the compiler enforces that every outcome is handled. AuthController.java:88-101

How the identity is actually verified

The browser does the OAuth dance with Google and hands us an ID token — itself a JWT, signed by Google. The backend never sees a password and has no client secret and no redirect URI. That is why the dependency is the bare spring-security-oauth2-jose artifact rather than the oauth2-client starter, and the pom.xml says so in a comment.

Other decisions in loginWithGoogle AuthService.java:162-200 worth knowing:

  • A new Google account is always a CUSTOMER. Google supplies no role, and becoming a worker means uploading documents and waiting for approval — that belongs on the worker signup form, not behind a one-click button.
  • passwordHash is set to null, not to some unusable sentinel value. The login path then has a clean, honest branch for "this account has no password".
  • Linking an existing account fills in the avatar only if it is empty — it will not overwrite a picture the user deliberately uploaded.
  • Any half-finished OTP signup for that address is discarded, so a live code can't be left pointing at an account that now exists by another route.

The 202 handoff: the Google credential is stashed in the same in-memory module variable used by worker signup, read exactly once on mount, and a missing one bounces straight back to /login. CompleteGoogleSignup also shows which Google account was picked, because a browser signed into several can hand back the wrong one.

4.5 · Posting a task and hiring a worker

What the user sees

Hiring a named worker

  2. Is it still OPEN?

  4. Are they APPROVED and not suspended?

The domain point behind step 5

A customer choosing a worker is making an offer. The worker has not agreed to anything yet, so the task cannot go straight to assigned — it goes to REQUESTED, and the worker can decline, which returns it to OPEN for anyone else. Getting this right is the difference between a marketplace and a work-allocation system.

4.7 · Payments — the most involved flow

What the user sees

After a worker accepts, a Pay advance button appears. Checkout shows the amount and offers eSewa or Khalti; the browser leaves the site, pays, and comes back to a "verifying…" screen that turns into a receipt. When the worker finishes, the same checkout reappears for the remaining 90%, this time also offering Cash.

The two instalments

advanceFor(budget) = budget × advanceRate          // 10%, rounded HALF_UP to 2dp
balanceFor(budget) = budget − advanceFor(budget)   // NOT budget × 0.9

PaymentService.java:93-104. The balance is subtracted rather than multiplied so the two legs always add back up to exactly the budget, no matter how the advance rounded. On a budget of NPR 2,505 the advance is 250.50 and the balance is 2,254.50 — multiplying by 0.9 would have given 2,254.50 too here, but not for every input. This is the kind of one-line detail that reads as care.

The two gateways behave completely differently

The answer to "how do you know the payment really happened?"

We never trust the browser. The browser coming back with a success parameter proves nothing — anyone can type that URL. When the callback page posts to /api/payments/esewa/verify, the server turns round and asks eSewa's own status endpoint whether that transaction actually completed, and compares the amount. Khalti has an extra wrinkle: the pidx is stored on the payment row before the redirect initiateKhalti:340, and the return trip is looked up by that stored value. That is what stops one customer from confirming another customer's payment by pasting their pidx.

Cash — the third way to pay the balance

Cash cannot be verified by any third party, so it is modelled as a two-sided declaration:

  1. Customer picks Cash at checkout → POST /api/payments/balance/cash → a PENDING payment row with provider CASH, and a notification to the worker. The task stays in AWAITING_PAYMENT. The source comment is blunt about it: "this notification is the whole mechanism". declareCashBalance:150-172
  2. The worker sees it on their Earnings/My Jobs screen and either confirms receipt → settle() → the job closes, or rejects → the row goes FAILED, the task stays payable, and the customer is told. confirmCashReceipt:181 / rejectCashReceipt:201
Why the worker's cash endpoints live on a different controller

/api/payments/** is hasRole("CUSTOMER") as a blanket rule. The worker's half of the cash handshake therefore could not live there, so it sits on WorkerPaymentController at /api/worker/payments/{taskId}/cash/confirm, under the hasRole("WORKER") rule. A small thing, but it is the honest reason for what otherwise looks like an odd split.

Things to admit before you are asked
  • It is all sandbox. eSewa's EPAYTEST merchant and Khalti's dev endpoints. No real money moves. Production URLs and a real key are wired through application-prod.properties as environment variables.
  • There is no refund flow. A cancelled task with a settled advance has no automated way back. That is a genuine gap, and saying so is better than being caught by it.
  • The eSewa signed-callback fallback is the one path where the gateway is not independently consulted. It is defensible — the HMAC secret is shared only with eSewa — but it is the weakest link in this flow and you should be the one to name it.

If the user closes the tab mid-payment: the payment row simply stays PENDING. Nothing is corrupted. Starting checkout again calls cancelPendingLeg, which cancels the stale row for that leg before creating a new one. And because completeEsewa/completeKhalti return an already-COMPLETED payment unchanged, refreshing the callback page is safe.

4.8 · Reviews and ratings

What the user sees

A Reviews page listing finished jobs that have not been reviewed yet. Pick stars, write a comment, submit. The worker's public rating on the browse page moves.

POST /api/reviews → ReviewService.java:34-66. Four gates, in order:

  1. Is this the caller's own task? → else 404.
  2. Is the status COMPLETED? → else InvalidOperationException.
  3. Is there an assigned worker to review?
  4. Has it already been reviewed? → reviewRepository.existsByTaskId.
Two things to say here that connect the whole system

First: gate 2 is silently strict. COMPLETED is only ever reached through markPaidInFull, which only a settled balance payment calls. So a task cannot be reviewed until it has been paid for in full. That is not enforced by a check in this class — it falls out of the state machine, which is a much stronger guarantee.

Second: gate 4 is belt-and-braces. The real guarantee is at the database level — Review.task is a @OneToOne with a unique constraint on task_id. Even two simultaneous requests cannot both succeed.

After saving, applyRatingToWorkerProfile :87-102 recomputes the running average — (oldAverage × oldCount + newRating) / newCount, 2dp HALF_UP — and writes ratingAverage and ratingCount back to worker_profiles. Those are exactly the numbers that appear on the worker cards in §4.5, which closes the loop: review → profile → discovery → next hire.

4.9 · Admin

There are two admin interfaces, and they share the same services

This is a deliberate demonstration of the same business logic behind two different presentation layers, and it is very likely to be asked about.

  • React admin pages at /admin/* in the SPA, calling /api/admin/** with a bearer token.
  • A server-rendered Thymeleaf console at http://localhost:8080/admin, with its own form login, a session cookie, CSRF tokens, a one-session-per-admin rule and an idle-timeout warning. Its AJAX endpoints live at /admin/api — deliberately not /api/admin, so the two never collide. AdminWebController.java, AdminWebApiController.java

Same AdminService, same ReportService, same JasperReports templates. Different authentication.

Approving a worker

  1. UI AdminVerificationQueue loads pending workers and clearance renewals together. Documents open through DocumentLink, which fetches them as blobs (see §4.12).
  2. HTTP PATCH /api/admin/workers/{id}/approve, no body. The whole controller sits behind "/api/admin/**" → hasRole("ADMIN") SecurityConfig.java:222.
  3. Service AdminService.approveWorker :249-259: 404 if no such user, 400 if they are not a worker, set APPROVED, clear any stale rejectionReason, save, email them.
  4. Effect getApprovedWorkerOrThrow starts passing for that worker. That single status change is what unlocks accepting jobs.

The queue itself is findByRoleAndStatusOrderByCreatedAtAsc(WORKER, PENDING) filtered to those with verificationSubmittedAt != null — someone who signed up but never uploaded documents does not clutter the queue. Rejection stores the reason as well as emailing it, because WorkerLayout repeats it back to the worker in a banner.

A genuinely subtle piece of code · AdminService.send :353-361

This is the one place in the service that catches an exception and swallows it. That looks like bad practice until you see why: EmailDeliveryException escaping a @Transactional method would mark the transaction rollback-only, and the approval itself would be undone because the notification email bounced. Catching it inside the method keeps the admin's decision. The boolean result rides out to the UI on AdminUserResponse.emailSent, so the admin is told the notice did not go out rather than it failing silently.

Suspension

PATCH /api/admin/users/{id}/suspend with a mandatory reason :308-314. Three things then happen without any further code:

  • Login throws SuspendedAccountException (403) carrying the reason.
  • Existing sessions die immediately — JwtAuthFilter refuses to authenticate a suspended principal even with a perfectly valid, unexpired JWT JwtAuthFilter.java:43-44. This is the payoff for keeping the role out of the token.
  • A refresh attempt revokes every refresh token for the account.

Admins cannot suspend other admins, and GET /api/admin/users/{id} returns 404 for an admin's id rather than 403 — so the endpoint cannot be used to work out who the administrators are.

Reports

GET /api/admin/reports/{slug}?format=pdf&from=&to= → ReportService → JasperReports, from .jrxml templates in resources/reports/, as PDF or Excel. Three reports: revenue, task summary, worker performance. Compiled templates are cached in a ConcurrentHashMap so the compile cost is paid once.

ReportType.fromSlug is a closed set that throws on anything unknown — which is precisely what stops a crafted slug being used to load an arbitrary file off the classpath. The download goes through axios as a blob with the filename parsed out of Content-Disposition, because a bearer token cannot ride along on a plain <a href>.

4.11 · Chat

What the user sees

A Messages screen with a list of people on the left and the conversation on the right, on both the customer and worker dashboards. Photos and files can be attached. Ticks show when the other side has read a message. A conversation only appears once the advance has been paid.

Two structural decisions

A conversation is per pair, not per task

The key is c{customerId}-w{workerId}, e.g. c12-w7 ConversationKey.java. A conversation spans every task that pair shares, so hiring the same plumber again continues the same thread rather than starting a blank one. The key doubles as the STOMP topic suffix.

Unpaid threads are invisible, not read-only

ChatAccessService.unlockedSharedTasks :37-50 returns the shared tasks whose advance is COMPLETED. If none, it returns an empty list — exactly what "these two people have no shared task" returns. So an unpaid thread is not listed, not counted, and 404s if addressed directly. There is no state for a user to probe.

Sending a message goes over the socket, not HTTP

  1. Browser client.publish({ destination: `/app/conversations/${key}/send`, body: JSON.stringify({ content }) }) ChatContext.jsx:201-209
  2. Server @MessageMapping("/conversations/{conversationKey}/send") → messageService.sendTextMessage(principal.getName(), key, content) ChatWebSocketController.java:19-26
  3. Service resolveConversation re-checks membership and the paid gate, hangs the message off the newest shared task, saves it, then broadcasts twice.
Why every message is published on two streams
  • /topic/conversations/{key} — reaches whoever currently has that thread open.
  • /user/queue/chat — reaches the recipient anywhere in the app. This is what keeps the unread badge in the sidebar moving while the thread is closed.

The same pair of broadcasts carries read receipts, so the sender's ticks flip and the reader's other tabs clear at the same time.

How the socket is secured

This is a good question to be asked, because "we put JWT on the REST API" is only half an answer if there is a WebSocket sitting next to it.

  • /ws/** is permitAll at the HTTP layer — the handshake has to get through. Authentication happens one layer in.
  • StompAuthChannelInterceptor on CONNECT reads the Authorization native header, validates the JWT exactly as the HTTP filter does, and attaches the principal to the STOMP session. No token → AccessDeniedException.
  • On every SUBSCRIBE and SEND it matches the destination against /(?:topic|app)/conversations/(c\d+-w\d+) and re-checks both participation and the paid-advance gate. The source comment is exactly the point: "so the socket cannot be used to get around the REST gate" StompAuthChannelInterceptor.java:96-97.

Deleting is a soft delete — the row survives as a tombstone with content and attachment nulled, the file is removed from disk, and the deletion is broadcast so open threads update. Only the sender can delete their own message.

4.12 · Protected file access

This started as a real bug, and the fix is the interesting part

Uploads used to be served by a static resource handler on /uploads/** with permitAll. That meant anyone with the URL could download a worker's citizenship document or police clearance — no login required, and the filenames are in the API responses.

The handler was removed. /uploads/** is now deliberately absent from the security config, and there is a comment there saying why so nobody adds it back SecurityConfig.java:199-202. Everything now goes through /api/files/**, which is authenticated() and checks ownership file by file.

GET /api/files/{filename} → FileAccessService.assertCanRead :52-92 resolves /uploads/<name> back to whatever record references it, then decides:

The file is…Readable by
anything, if the caller is an ADMINallowed
a chat attachmentthe two participants of that conversation
a police clearance, citizenship doc, or pending renewalthe owning worker only (plus admins)
a profile photo or account avatarany signed-in user
referenced by nothingnobody — 404

Every denial is a 404, never a 403 — same reasoning as everywhere else in the codebase. Responses carry X-Content-Type-Options: nosniff, Cache-Control: private, and Content-Disposition: attachment for anything that is not an image.

"Why does the frontend download images as blobs?"

Because <img src="/api/files/abc.png"> is a plain browser request and there is no way to attach an Authorization header to it. So fileApi.js fetches the file through axios with responseType: "blob", wraps it in an object URL, and hands that to the <img> — see AuthedImage.jsx and DocumentViewerModal.jsx. Callers revoke the object URL afterwards so the blob is not leaked.

This is the direct, visible cost of having secured the uploads properly, and it is a good story: a security fix that forced a real frontend change.

Upload safety on the way in

  • Content type must be in a fixed allow-list.
  • Magic bytes are then checked against the declared type — JPEG FF D8 FF, PNG's 8-byte signature, %PDF, PK\x03\x04 for docx, and so on. The declared type is client-supplied and worth nothing on its own. FileStorageService.java:84-122
  • Stored under a fresh UUID — a user-supplied filename never becomes a path.
  • resolveForRead normalises the path and re-checks it is still inside the upload directory, defeating ../ traversal.
  • 10 MB per file and per request.

Authorization — three layers, and one of them is empty

Be the one who says this, don't get caught by it

@EnableMethodSecurity is switched on at SecurityConfig.java:35, and the comment above it describes method annotations as "a second line, closer to the data". But there is not a single @PreAuthorize, @PostAuthorize or @Secured anywhere in src/main. The capability is enabled; that layer was never populated.

The honest and correct answer if asked: the checks that layer would have carried do exist — they are hand-written in the service methods, which is where the ownership rules actually live. The annotation is switched on ready for them to be moved there. Saying that is much stronger than being shown an empty grep result.

  1. Layer 1 — URL rules · this is where role authorization lives SecurityConfig.java:196-235. Order matters — the first matching rule wins. /api/admin/** → ADMIN; /api/worker/** → WORKER; /api/payments/**, /api/reviews/** → CUSTOMER; /api/public/** GET only → open; everything unlisted → authenticated.
  2. Layer 2 — method annotations · enabled but unused See the box above.
  3. Layer 3 — ownership checks in services · the real second line TaskService.ensureCanView:349 and ensureAssignedTo:342, PaymentService.getOwnTaskOrThrow:641, MessageService.resolveConversation:284, NotificationService via findByIdAndUserId, FileAccessService.assertCanRead:52, StompAuthChannelInterceptor.authorizeConversationAccess:69. All of them throw 404, never 403 — a consistent, deliberate choice so records cannot be enumerated by watching status codes.

The classic three

SQL injection

Nothing anywhere builds SQL by string concatenation. Every query is either a Spring Data derived method name or a @Query with named parameters, which JDBC binds separately from the statement text. Grep for "SELECT " + and you get nothing.

XSS

React escapes interpolated values by default and there is no dangerouslySetInnerHTML. Thymeleaf's th:text auto-escapes on the console side. On top, the API chain's CSP is default-src 'none'; sandbox, which matters most for uploaded files served from our own origin — they cannot execute.

CSRF

On for the cookie-authenticated console, off for the header-authenticated API — with the reasoning written into both chains. See §1.

Brute force

5 failed logins → 15-minute lock, with the remaining minutes returned as a 423. Counters reset on a successful sign-in. AuthService.java:40-41, 280-288

Response headers, both chains

X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin, HSTS for one year including subdomains, and a Content-Security-Policy tuned per chain.

Weaknesses — know them before someone else finds them
  • Tokens live in localStorage. Any script that gets injected can read them, and the 7-day refresh token sits beside the 15-minute access token. Mitigations in place: a very strict CSP, no dangerouslySetInnerHTML, a short access-token life, and a refresh token that can be revoked and that detects replay. The stronger design is an httpOnly cookie plus a CSRF token — that is the honest answer to "what would you change".
  • A database query per authenticated request. Deliberate — it is what makes suspension instant — but uncached. A short-TTL cache keyed on email would fix it.
  • WorkerService.listAvailableWorkers filters in memory :38-47, after loading every approved worker and doing one findByUserId each — a classic N+1. Fine at coursework scale, wrong at real scale; the fix is a single join query with the filters in the WHERE clause.
  • Real secrets sit in application.properties — a Gmail app password, the JWT signing key, database credentials. The file is gitignored, and the production profile reads every one of them from an environment variable with no default, so a misconfigured production boot fails loudly rather than starting with development values. Still: that app password should be rotated.

9 · Question bank

What is it, and how does the business work

What does SewaSathi actually do?Non-technical

It connects people in Nepal who need a household job done — plumbing, cleaning, moving, repairs — with local workers who do that job. The customer describes the work and a budget, a verified worker takes it on, and the platform handles the messaging, the payment in two instalments, and the review afterwards.

Who are the users?Non-technical

Three roles, and the code has exactly three: Customer posts and pays, Worker does the job and gets paid, Admin approves workers and polices the platform. The role is stored on the user row and decides which dashboard you see and which API calls you are allowed to make.

Why does the customer pay 10% up front instead of everything at the end?Non-technical

It protects the worker. Without it, a customer could book someone, have them travel across Kathmandu, and vanish. The advance is a commitment. It is also the switch that turns the booking real in the system: only once it settles does the task become ASSIGNED, the worker get the go-ahead, and the chat between the two unlock.

What stops a fake or dangerous worker signing up?Non-technical

Four things. They must verify a real email address with a code before the account exists. They must upload a police clearance certificate and citizenship document. An admin has to look at those and approve them — until then they physically cannot accept a job, checked on the server, not just hidden in the UI. And the police clearance expires after six months and has to be renewed.

What if the worker takes the job and never turns up?Non-technical

The task sits in ASSIGNED and never progresses; the customer has only paid the 10%, not the full amount, and the balance is never due. There is no automated refund flow — that is a genuine gap I would fix next, along with letting a customer un-assign a non-starting worker. I would rather say that than pretend it is handled.

How does the platform make money?Non-technical

The commission model is not implemented — currently the full budget flows to the job and the 10% is an advance, not a fee. The natural place to add it is PaymentService.settle(), where every payment already passes through: split the amount and record the platform's share.

Can a customer pay in cash?Non-technical

For the final 90%, yes. Cash cannot be verified by any third party, so it is a two-sided handshake: the customer declares they paid cash, the worker gets a notification, and the job only closes when the worker confirms they actually received it. The worker can also reject the claim, and the task stays payable. The 10% advance must go through a gateway.

Why do the customer and worker only get to chat after payment?Non-technical

To stop people using the platform to find each other and then arranging the job privately off it. Contact details are worth something; unlocking them at the moment of commitment is the standard marketplace answer. Technically it is enforced in one small class, ChatAccessService, and — importantly — an unpaid conversation is invisible rather than merely read-only.

What happens if someone abuses the platform?Non-technical

An admin suspends the account with a written reason. It takes effect immediately — their existing login stops working on their very next request, not when some timer expires — and the reason is shown to them when they try to sign in.

Is this live? Is real money moving?Non-technical

No. Both gateways are in sandbox mode — eSewa's EPAYTEST merchant and Khalti's development endpoints. The payment flow is complete and real; only the money is fake. Switching to production is a configuration change, not a code change: the production profile already reads live URLs and a real key from environment variables.

Architecture

Why Spring Boot and React rather than something else?Technical

Spring Boot gives security, ORM, validation, WebSocket, mail, templating and scheduling as one coherent, well-documented stack, which matters when one person is building all of it. React with Vite gives a fast dev loop and a component model that suits a dashboard-heavy app. They are also the stack the coursework requirements point at — Hibernate, Spring MVC, Thymeleaf, JSP-style server rendering are all named.

Explain a REST API in one sentence.Non-technical

The browser asks the server for things using ordinary web addresses and standard verbs — GET to read, POST to create, PATCH to change, DELETE to remove — and the server answers with data rather than a web page.

What is the difference between a controller and a service?Technical

The controller is the doorway: it maps a URL, binds and validates the request body, pulls the identity off the security context, and returns a status code. It contains no business logic. The service holds the rules — can this person do this, is the task in the right state, what happens next — and owns the transaction. Look at TaskController.assignWorker: five lines, one delegation. All the actual thinking is in TaskService.assignWorker.

What is dependency injection, and where is it in your code?Technical

A class declares what it needs and is handed it, rather than constructing it itself. Here every bean takes its collaborators through a constructor — mostly generated by Lombok's @RequiredArgsConstructor from private final fields, as in AuthService. Two classes write the constructor by hand, PaymentService and AdminService, because they need @Value on a constructor parameter and Lombok cannot copy an annotation there. Constructor injection over field injection because it makes dependencies impossible to miss, keeps fields final, and means the class can be unit-tested with plain new and mocks.

Why return DTOs instead of the entity?Technical

Three reasons. Leakage: User carries passwordHash and failedLoginAttempts; UserResponse carries neither. Lazy loading: open-in-view=false closes the Hibernate session before Jackson runs, so serialising an entity with a lazy association would throw — building the DTO inside the transaction avoids that. Decoupling: the JSON shape can change without a schema migration and vice versa.

Why are there two front-ends?Technical

The React SPA is the product. The Thymeleaf console at /admin demonstrates server-side rendering with Spring MVC, session management with timeouts, and CSRF protection — things a stateless JSON API deliberately does not do. They share the same AdminService and the same report templates, so it is genuinely one application with two presentation layers rather than two systems.

Is this a monolith or microservices? Would you split it?Technical

A modular monolith, and deliberately so. One team, one database, one deployment — microservices would add network calls, distributed transactions and operational overhead to buy independent scaling nobody needs yet. The package structure is already split by concern, so the seams exist if it ever had to be broken up. Payments and notifications would be the first candidates.

How would this scale? What breaks first?Technical

Three things, in order. The per-request database lookup in JwtAuthFilter — fix with a short-TTL cache. listAvailableWorkers, which loads every approved worker and filters in memory with an N+1 — fix with one join query. The in-memory STOMP broker, which does not work across multiple instances — fix by putting a real broker like RabbitMQ behind it. Uploads on local disk would also have to move to object storage.

Why is there no API documentation / Swagger?Technical

There isn't one, and it would be a reasonable addition — springdoc-openapi is one dependency and would generate it from the existing annotations. The endpoints are documented in this file instead.

How do the frontend and backend agree on data shapes?Technical

By convention, not by a shared type — the frontend is plain JavaScript with no TypeScript, so nothing checks that TaskResponse and what the component expects match. That is the honest weakness of the setup. TypeScript plus generated types from an OpenAPI spec would close it. What does protect it is that all HTTP calls live in the twenty modules under src/api/, so there is exactly one place per endpoint where the shape is assumed.

Authentication & security

How are passwords stored?Non-technical

They are never stored. What is stored is a BCrypt hash — a scrambled fingerprint that cannot be turned back into the password. When someone signs in we scramble what they typed the same way and compare the two fingerprints. If the database leaked, the attacker would not have anyone's password.

What is BCrypt and why not SHA-256 or MD5?Technical

BCrypt is a password hashing function that is deliberately slow and embeds a random salt in its own output. Slow matters because an attacker with a leaked database wants to try billions of guesses per second — BCrypt reduces that to thousands. The salt means two users with the same password get different hashes, so precomputed rainbow tables are useless. MD5 and SHA-256 are fast general-purpose hashes; being fast is exactly the wrong property here.

What is a JWT?Non-technical

A signed pass. After you log in, the server gives your browser a small piece of text carrying your identity, cryptographically signed with a secret only the server knows. Your browser shows it with every request. The server checks the signature, and if it is valid it trusts the contents without having to remember anything about you between requests — which is what makes it "stateless".

What is inside YOUR token, specifically?Technical

Three claims: sub (the user's email), iat, exp. Signed HS256. That is all — no role, no user id, no name. See JwtService.java:27-36. This is the question most likely to be followed by "why?" — see the next entry.

Why isn't the role in the token? Wouldn't that save a database query?Technical

It would, and I chose not to. A JWT cannot be recalled once issued. If the role lived inside it, suspending an account would do nothing until the token expired — the suspended user would keep working for up to fifteen minutes. Instead the filter re-reads the user on every request and refuses if they are now suspended, so a suspension takes effect on the very next click. The cost is one indexed lookup per request, which I would cache with a short TTL if it ever mattered. Immediate revocation was worth more than the query.

What happens when the token expires while I'm using the site?Technical

Nothing visible. The server returns 401; the axios response interceptor catches it, calls /auth/refresh with the refresh token, gets a new pair, and replays the original request. The user sees a slightly slower click. If the refresh also fails — revoked, expired, or idle too long — the tokens are cleared and they are signed out. httpClient.js:57-93

What is a refresh token and why rotate it?Technical

The access token is short-lived and cannot be revoked, so it cannot be what keeps someone signed in for a week. The refresh token can: it lives in the database, so it can be revoked. Rotation means each refresh spends the old token and issues a new one, so a stolen copy stops working the moment the real user refreshes again. Better still, if a spent token is ever presented again we know something is wrong and revoke the entire session family rather than serve the attacker. RefreshTokenService.java:77-84

Why is the refresh token hashed with SHA-256 rather than BCrypt?Technical

Because BCrypt's slowness buys protection against guessing, and there is nothing to guess: the token is 256 bits of SecureRandom. All the slowness would do is tax every refresh lookup. It is still hashed, so a database leak does not hand over live sessions.

Why is CSRF disabled? Isn't that a vulnerability?Technical

It is disabled on the API chain only, and that is correct there. CSRF works because browsers attach cookies automatically, even to requests triggered from an attacker's page. Our API authenticates from an Authorization header that JavaScript must set deliberately, and the attacker's page cannot read our token. So a forged request arrives with no credentials at all. The admin console does authenticate from a cookie, and CSRF is switched on there.

How do you prevent SQL injection?Technical

No SQL is ever built by string concatenation. Every query is either a Spring Data derived method name, which Spring generates, or a @Query with named parameters that JDBC binds separately from the statement text — so a value can never be parsed as code. Grep the repository package for string concatenation and there is none.

How do you prevent XSS?Technical

Layered. React escapes everything it interpolates and we never use dangerouslySetInnerHTML. Thymeleaf's th:text auto-escapes on the console side. And the API chain sends Content-Security-Policy: default-src 'none'; sandbox, which matters most for uploaded files: they are served from our own origin, so without that header an uploaded HTML file would be a stored-XSS vector.

Storing the token in localStorage — isn't that insecure?Technical

It is the weakest point in the design and I know it. Anything that achieves script execution on the page can read localStorage, including the seven-day refresh token. What mitigates it: a very strict CSP, no raw HTML injection anywhere, a fifteen-minute access token, and a refresh token that is revocable and detects replay. The stronger design is an httpOnly cookie the browser will not expose to JavaScript, plus a CSRF token — that is what I would change with more time. The reason it is not that today is that the SPA and API are on different origins in development, which makes cookie handling considerably more fiddly.

What stops one customer reading another customer's data?Technical

Two independent layers. The URL rules say what role can hit an endpoint. Then every service method re-checks that the caller owns the specific record — the identity comes from the security context, never from the request body, so there is no id to tamper with. Ask for someone else's task and you get 404, not 403, deliberately: a 403 would confirm the record exists and let you count them.

What happens after five wrong passwords?Non-technical

The account locks for fifteen minutes and the response tells you how many minutes are left. The counter resets on a successful sign-in. It uses HTTP status 423 Locked, which is distinct from a plain "wrong password" 401, so the UI can say something useful.

How does Google Sign-In actually prove who I am?Technical

The browser gets a signed ID token from Google. Our server verifies it against Google's published public keys, checks the issuer, checks it has not expired, and — the critical one — checks the audience matches our own client id. Without that last check, a valid Google token issued for any other app would be accepted here. We additionally require Google to assert email_verified, which is what makes it safe to link to an existing password account by email address.

Could someone forge a JWT?Technical

Not without the signing key. It is HS256 with a 512-bit secret; changing a single character of the payload invalidates the signature and the parse throws. The realistic attacks are stealing the key — which is why it is an environment variable in production, never a literal — or stealing a token from a browser, which is the localStorage concern above.

Your @EnableMethodSecurity is on but I see no @PreAuthorize. Why?Technical

Correct, and a fair catch. The annotation is enabled and the comment beside it describes method-level checks as a second line of defence — but that layer was never populated. The checks it would have carried do exist: they are written by hand inside the service methods, because most of them are ownership checks ("is this your task?") rather than role checks, and those need to load the record anyway. Moving the role parts onto annotations would be a tidy-up, not a security fix.

Database and ORM

What is Hibernate / JPA?Non-technical

A translator between Java objects and database tables. I write a normal Java class called Task; Hibernate creates and maintains a tasks table to match it, and turns taskRepository.save(task) into the right SQL. JPA is the standard; Hibernate is the implementation of it.

Show me a relationship in your entities.Technical

Task has two @ManyToOne links to User — customer and assignedWorker — because both parties are users. WorkerProfile is @OneToOne with User: worker-specific fields do not belong on every account. Review is @OneToOne with Task and the task_id column is unique, which is what enforces one review per job at the database level rather than trusting application code.

What is lazy loading, and why open-in-view=false?Technical

Lazy loading means a related object is not fetched until you touch it, so loading a task does not drag in the whole customer row unnecessarily. open-in-view defaults to true, which keeps the Hibernate session open through view rendering — convenient, but it hides N+1 queries and lets database access sneak into serialisation. Setting it false forces everything to be loaded inside the service's transaction, which is exactly why every response is built as a DTO there.

ddl-auto=update in development but validate in production — why the difference?Technical

update lets Hibernate patch the schema as I change entities, which is right while the design is moving. In production it would be dangerous: it is silent, it never removes anything, and a bad entity change could quietly alter live tables. validate instead compares the entities to the live schema and refuses to start if they disagree — a loud failure at boot rather than a mystery at runtime. Schema changes there are applied deliberately.

Why no Flyway or Liquibase?Technical

Single developer, single environment, and Hibernate handles the additive changes in development. What Hibernate cannot do is modify an existing column, so nine hand-written scripts live in resources/db/ for exactly those cases — widening the tasks.status enum to add REQUESTED, and making password_hash nullable for Google accounts. That is the honest state of it. Flyway becomes necessary the moment a second person or a second environment is involved, and it is what I would add first for a real deployment.

Do you have any indexes?Technical

Yes, and placed for specific queries rather than sprinkled around. users.email is unique — every request looks up by it. notifications has a composite index on (user_id, is_read) for the unread count and one on created_at for ordering. messages has (task_id, sender_id, read_at) for unread counting. refresh_tokens.token_hash and payments.transaction_uuid / provider_ref are unique, which serves as both index and correctness guarantee.

Give me an example of a non-trivial query.Technical

TaskRepository.topCategories(from, to, Limit) — a JPQL aggregate that groups tasks by category over a date range and returns counts, used by the admin analytics. WorkerProfileRepository.workerPerformance() uses a correlated subquery to attach earnings to each worker. And ReviewRepository.publishableTestimonials(minRating, Limit) feeds the public homepage. All parameterised, none concatenated.

Why is read called is_read in the notifications table?Technical

Because read is a reserved word in MySQL. The Java field is read; @Column(name = "is_read") maps it. A small detail, but it is the kind of thing that shows the schema was actually run rather than only compiled.

Payments

How do you know a payment really happened?Technical

We never trust the browser. The browser returning to a success URL proves nothing — anyone can type that address. When the callback page reports back, the server independently calls the gateway's own status API and asks whether that transaction completed, and compares the amount. Only then is the payment marked complete and the task moved on.

Could I fake a successful payment by crafting the callback URL?Technical

No. For Khalti there is no path at all — the server looks the payment up by the pidx it stored before the redirect and asks Khalti directly; a made-up pidx matches no row. For eSewa, the callback is HMAC-signed with a secret shared only with eSewa, and it is only consulted at all if eSewa's status endpoint is unreachable — and even then the amount must match. That fallback is the single weakest link in the flow, and I would rather name it than have it found.

Why two instalments rather than one payment?Non-technical

It balances the risk. The 10% up front means the worker is not travelling out on a booking that might evaporate. The 90% at the end means the customer is not fully paid out before the work is done. It also gives the system a clean signal for "this booking is real", which is what unlocks chat and lets the worker start.

What if the user closes the tab in the middle of paying?Technical

The payment row stays PENDING and nothing is corrupted. Returning to checkout cancels the stale row for that leg before starting a new one, so there is never more than one live attempt. And because verification returns an already-completed payment unchanged, refreshing the callback page is harmless.

What stops a duplicate callback counting the job twice?Technical

Two guards. Verification returns early if the payment is already COMPLETED. And TaskService.markPaidInFull — the only thing that moves a task to COMPLETED — is a no-op unless the task is currently in AWAITING_PAYMENT, so a second call cannot increment the worker's completed-job count again.

What if the worker lies and says they never got the cash?Non-technical

The task stays in AWAITING_PAYMENT and the customer is notified that the claim was rejected. The system deliberately does not try to adjudicate — it has no way to know who is telling the truth. In a real product this is where a dispute queue for admins would go, and that is the honest answer rather than pretending the model handles it.

Why is the balance subtracted rather than multiplied by 0.9?Technical

So the two instalments always add up to exactly the budget regardless of rounding. If both legs were computed by multiplication and each rounded independently, there would be inputs where they sum to a paisa more or less than the budget. Subtracting the advance from the budget makes that impossible by construction. PaymentService.java:97-104

Why does eSewa need an HTML form and Khalti doesn't?Technical

Different integration styles. eSewa ePay v2 expects a form-encoded browser POST it can render a payment page for — it cannot be an XHR, which is why the frontend builds a real <form> with hidden inputs and submits it. Khalti is server-to-server: our backend calls their initiate API, gets back a URL, and the browser is simply redirected. It also explains why the Vite dev server pins port 5173 with strictPort — eSewa redirects back to a fixed URL, so the port must not drift.

Are refunds handled?Non-technical

No. A cancelled task with a settled advance has no automated route back, and neither gateway's refund API is integrated. It is a known gap.

Real-time — notifications and chat

Are notifications polled, or pushed?Technical

Pushed, over a WebSocket, and stored in the database. Both, because they do different jobs: the push makes the bell move immediately, the row means the notification survives a refresh, a reconnect, or the user simply not being online when it happened. The client fetches recent history over REST on mount and merges live events into it.

What are WebSocket, STOMP and SockJS?Non-technical

A WebSocket is a connection that stays open, so the server can speak first instead of waiting to be asked. STOMP is a small messaging grammar layered on top — subscribe to this channel, send to that one — so it isn't just a stream of unlabelled bytes. SockJS is the fallback that keeps things working on networks or proxies that block raw WebSockets.

How is the WebSocket authenticated? Isn't /ws public?Technical

The HTTP handshake is permitAll, because it has to get through before there is a STOMP session to authenticate. Authentication happens one layer in: StompAuthChannelInterceptor reads the bearer token from the CONNECT frame's headers and validates it exactly as the HTTP filter does. Better still, it re-checks every SUBSCRIBE and SEND against the conversation key, so the socket cannot be used to reach a conversation the REST API would refuse. That is a real question and a common gap in projects with a WebSocket bolted on.

What happens when the connection drops?Technical

The STOMP client reconnects automatically every four seconds and re-subscribes. Nothing is lost, because every message and notification is already a database row — on reconnect the client refetches and reconciles. This is the practical payoff of not being push-only.

Why does a message get broadcast twice?Technical

Two audiences. /topic/conversations/{key} reaches whoever currently has that thread open. /user/queue/chat reaches the recipient anywhere in the app, which is what makes the unread badge move while the thread is closed. Read receipts travel the same pair, so the sender's ticks flip and the reader's other tabs clear together.

Files and uploads

Where do uploaded files go?Technical

To an uploads/ directory on the server's disk, each under a freshly generated UUID filename — a user-supplied name never becomes a path. The database stores only the URL. For a real deployment this should be object storage, since local disk does not survive a redeploy and does not work across multiple instances.

Can anyone download a worker's citizenship document?Technical

No — and it is worth knowing that they once could. Uploads used to be served by a static handler with permitAll, so anyone with the URL could fetch a police clearance. That handler was removed and /uploads/** is now deliberately absent from the security config, with a comment saying why. Files go through /api/files/**, which requires a login and then checks per file: identity documents are readable only by the owning worker and admins, chat attachments only by the two participants, avatars by any signed-in user. Every denial is a 404.

What stops someone uploading a virus or a script?Technical

Layered, though not antivirus. The declared content type must be in a fixed allow-list; then the magic bytes are checked against it, because the declared type comes from the client and is trivially forged. Files are stored under a random UUID and served with nosniff, Content-Disposition: attachment for non-images, and the API chain's sandbox CSP — so even if something got through it cannot execute in a browser. Size is capped at 10 MB. Actual malware scanning would be the next addition.

Why fetch images as blobs instead of just using <img src>?Technical

Because <img src> is a plain browser request and there is no way to attach an Authorization header to it — so a protected file simply would not load. The app fetches through axios with responseType: "blob", wraps the result in an object URL and hands that to the image tag. It is the direct, visible cost of having secured uploads properly.

Errors, logging and operations

What did you actually test?Technical

38 files under src/test/java. Unit tests for the services with dependencies mocked — AuthServiceTest, PaymentServiceTest, TaskServiceTest, and focused ones like EsewaServiceTest for signature generation and FileStorageServiceTest for magic-byte validation. And integration tests that run real HTTP through the whole stack against an in-memory H2 database: SignupOtpIntegrationTest, RefreshFlowIntegrationTest, AuthLockoutIntegrationTest, AdminConsoleIntegrationTest, and SecurityBoundaryTest — that last one is the one to name, because it proves the role rules actually hold rather than assuming them.

What is the difference between your unit and integration tests?Technical

A unit test constructs one service with mocked repositories and checks its logic in isolation — fast, and it fails for exactly one reason. An integration test uses @SpringBootTest, boots the real application context with a real (in-memory) database, and makes real HTTP calls, so it verifies the wiring: security rules, JSON serialisation, transactions, validation. Both matter; a unit test cannot tell you the security config is right.

Why H2 for tests instead of MySQL?Technical

Speed and isolation. H2 runs in memory, so each test class gets a fresh schema in milliseconds with ddl-auto=create-drop, and the suite needs no database installed. It runs in MySQL-compatibility mode to keep the dialects close. The trade-off is real: H2 is not MySQL, so a MySQL-specific behaviour could pass here and fail in production. Testcontainers running actual MySQL is the more rigorous answer.

What happens if an unhandled exception is thrown?Technical

GlobalExceptionHandler catches it and returns a 500 with a generic, translated message — the stack trace goes to the log, never to the client, so internal details are not leaked. On the console side WebExceptionHandler renders a styled error page instead, carrying the correlation id so a user can quote one number.

What is a correlation id?Technical

A unique id attached to each request and carried on every log line it produces, so all the lines for one user's one click can be pulled out of a busy log. It is read from an incoming X-Correlation-Id header or generated, put in the logging MDC, echoed back on the response, and shown on error pages. It is also sanitised before use — an unsanitised header could be used to inject fake newlines into the log.

How would you debug a 500 in production?Technical

Get the correlation id from the user or the response header, grep the rolling log for it, and read the whole request in one block. Failing that, /actuator/health for liveness and /actuator/metrics — both admin-only in production. Production logs at INFO for our own packages and WARN for everything else, so the noise is manageable.

Where are the logs?Technical

Console plus rolling files under app.log-dir (logs/), split into a general log and an errors-only log, 10 MB per file, 30 and 90 days of history with a total size cap. Configured in logback-spring.xml, and the file appenders are disabled under the test profile so running tests does not litter the disk.

Is anything scheduled or running in the background?Technical

Three nightly cleanup jobs: expired signup OTP challenges at 03:15, expired password reset challenges at 03:25, and expired refresh tokens at 03:30. Without them those tables would grow forever with dead rows.

Frontend

What is a component, a hook, and context?Non-technical

A component is a reusable piece of interface — a button, a card, a whole page — described as a function that returns what it should look like. A hook lets a component remember things or run logic (useState, useEffect, or our own useNotifications). Context is shared state that any component can read without it being passed down by hand — which is how every screen knows who is signed in.

Why no Redux or Zustand?Technical

Because there is very little genuinely global state. Two contexts cover it — AuthContext for the session and ChatContext for the live socket — and everything else is server data fetched by the page that needs it. Adding Redux would be ceremony without benefit. What I would add is a server-cache library like TanStack Query, because several pages refetch the same data independently; that is a caching problem, not a state-management one.

How does routing work, and what is lazy loading?Technical

React Router 7 with all routes declared in App.jsx. Only the landing page, login and the route guard load eagerly; everything else is React.lazy, so each page is a separate bundle fetched on first visit behind a <Suspense> spinner. A visitor reading the homepage never downloads the admin dashboard. The three dashboards are nested routes under a shared layout, so the sidebar and header render once and only the inner outlet changes.

How does the app know who is logged in after a refresh?Technical

The tokens are in localStorage, but the user object is not — deliberately, so it cannot go stale. On boot, if a token exists, AuthContext calls GET /api/users/me and rebuilds the session from the server's answer; if that fails the tokens are cleared. So the UI can never show a signed-in state backed by a revoked token.

How are the routes protected?Technical

<ProtectedRoute role="CUSTOMER"> wraps each dashboard: it renders nothing while the session is still being restored, then either renders the page or redirects to /login remembering where you were headed. WorkerLayout adds a second gate for workers who are not yet approved. All of this is convenience, not security — it stops someone stumbling into the wrong screen, but the actual enforcement is entirely server-side. That distinction is worth stating explicitly if asked.

What is Tailwind, and where is the config file?Technical

Tailwind is utility-first CSS — you compose small classes like flex and rounded-card in the markup instead of writing separate stylesheets. There is no tailwind.config.js because this is Tailwind v4, which is configured in CSS: the whole design system — brand ramp, surfaces, ink colours, radii, shadows — is declared in an @theme block in src/index.css. That is why changing one hex there restyles the entire app.

What is the React Compiler doing in your build?Technical

babel-plugin-react-compiler is enabled in vite.config.js. It analyses components at build time and inserts memoisation automatically, so re-renders are avoided without hand-written useMemo and useCallback everywhere. It is opt-in and does not change how the code is written.

The uncomfortable questions

What happens if I type a URL that doesn't exist?Technical

Nothing renders. There is no catch-all * route in App.jsx, so an unknown path produces a blank page rather than a 404 screen. That is a real oversight and a two-line fix: a <Route path="*"> pointing at a NotFound component. The backend does have proper error pages — templates/error/404.html and friends — this gap is frontend-only.

Why is the JWT secret sitting in a properties file?Technical

In development, for convenience — and that file is gitignored, with a secret-free .example committed in its place. In production it is read from an environment variable with no default, so a missing JWT_SECRET makes the application refuse to start rather than silently fall back to a development key. Same pattern for the database password, the Khalti key and the mail credentials. The genuine issue is that the development file on my disk holds a real Gmail app password, which should be rotated.

Your README contradicts your code. Explain.Technical

It does, and the README is the one that is wrong. It still describes an earlier design where signup was email and password only, with no verification and no social login, and it marks email as not implemented. Since then OTP verification, password reset by email and Google Sign-In were all added, and the README was not updated. The code is the truth; this document describes the code. It needs fixing.

What is the weakest part of this project?Technical

Three, in order. Tokens in localStorage — an XSS would hand over a seven-day session; httpOnly cookies plus CSRF tokens would be stronger. No frontend tests at all — the backend is well covered, the React side is not covered whatsoever. No refund or dispute handling — the payment model assumes things go well, and the cash flow in particular has no way to resolve a disagreement.

What would you do differently if you started again?Technical

TypeScript on the frontend from day one — right now nothing checks that a component's assumptions about a response shape are correct. Flyway from the first commit instead of hand-applied SQL. Cookie-based auth rather than localStorage. And I would put the advance rate in one place rather than duplicating the constant across backend and frontend.

What is unfinished?Technical

Refunds, dispute resolution, the frontend 404 route, frontend tests, and the commission model. There is also a small piece of dead markup in Login.jsx — an empty prop slot with a comment referring to a "forgot password" link that was moved elsewhere. Harmless, but it should be cleaned up.
